验证思路：

## 1. 实验目标

围绕 MultiHop-RAG 的跨文档问答任务，构建一个能够检索资料、结合多篇文章进行推理并输出简短答案的 RAG 系统。

核心研究问题：**怎样让模型找全证据，并根据证据正确回答多跳问题？**

整体路线：

1. 跑通基础 RAG，得到初始成绩。
2. 分析错误，区分检索问题和回答问题。
3. 逐项改进检索和证据选择，进行对照实验。
4. 根据错误类型和数据质量，决定是否进行微调。
5. 完成全量评测、案例分析和项目交付。

## 2. 数据与模型的分工

| 组成 | 作用 |
| --- | --- |
| `corpus.json` | 609 篇英文文档，作为外部知识库 |
| `MultiHopRAG.json` 的 `query` | 提供 2,556 道待回答的问题 |
| `answer` | 在独立评分阶段作为参考答案 |
| `evidence_list` | 在事后分析阶段检查参考证据是否被检索到 |
| BM25 | 根据关键词匹配检索文档片段 |
| MiniCPM4.1-8B | 阅读检索结果，推理并生成答案 |

当前基线的检索器和生成器不使用参考答案或标注证据作为输入，也不将它们加入索引。

**RAG 与微调是两个不同操作：**RAG 在回答时提供外部资料；微调通过训练修改模型的部分或全部参数。当前基线只做前者。

## 3. 阶段一：建立基础 RAG

### 3.1 处理知识库

将全部 609 篇文章切分成适合检索和输入模型的片段，保留标题、来源、发布时间、URL 和原文位置。

当前设置：

| 参数 | 设置 |
| --- | --- |
| 正文片段长度 | 250 个空白分隔词 |
| 相邻片段重叠 | 50 个词 |
| 片段总数 | 5,480 |
| 检索方法 | BM25 |
| 每题最多选择片段数 | 8 |
| 每篇文章最多选择片段数 | 2 |
| 生成模型 | MiniCPM4.1-8B，未微调 |
| 模型精度 | BF16 |
| 思考模式 | 关闭 |
| 解码方式 | 贪心解码 |
| 最大输入长度 | 6,000 tokens |
| 最大生成长度 | 128 tokens |

### 3.2 执行问答

对每道题依次执行：

1. 读取问题。
2. 从完整知识库中检索相关片段。
3. 在输入长度预算内组织证据上下文。
4. 将问题和上下文一起交给 MiniCPM。
5. 生成简短答案；证据不足时回答 `Insufficient Information`。
6. 保存实际上下文、原始输出、最终答案和资源记录。

该阶段不生成训练题，也不更新模型参数。

### 3.3 得到基线成绩

先完成少量题目，检查流程；再覆盖全部 2,556 道题。

前 10 题是调试子集，包含 7 道推理题和 3 道比较题，不能代表完整测试集的性能。当前的 10/10 是本地评分规则下的结果，不等于每道回答都与参考答案完全一致。

全量完成后，得到后续实验的参照成绩。

## 4. 阶段二：分析错误来源

先定位原因，再决定改进方法，避免只根据总准确率盲目微调。

| 错误类型 | 典型表现 | 可能的改进方向 |
| --- | --- | --- |
| 没检索到相关文章 | 问题与文章使用不同表达，关键词匹配失败 | 增加语义检索 |
| 没找全多跳证据 | 只找到一个对象的信息，漏掉另一个对象 | 改进多文档检索和覆盖 |
| 检索到了但未进入上下文 | 有用片段排名靠后，或被输入预算排除 | 重排序、调整上下文选择 |
| 上下文齐全但推理错误 | 比错数值、混淆事件时间、误读限定条件 | 改进提示词，尝试微调 |
| 证据不足仍然猜测 | 应回答信息不足，却输出确定答案 | 改进证据充分性判断和拒答 |

事后可利用 `evidence_list` 检查参考文档的覆盖情况，但不能让标注证据代替系统的真实检索。

## 5. 阶段三：逐步改进并进行对照

| 实验 | 方案 | 验证问题 | 状态 |
| --- | --- | --- | --- |
| A：基础基线 | BM25 + 原始 MiniCPM | 基础系统能达到什么成绩？ | 当前阶段 |
| B：混合检索 | BM25 + 语义检索 + 原始 MiniCPM | 能否找回关键词检索漏掉的证据？ | 计划 |
| C：证据重排序 | 在 B 的基础上增加重排序 | 能否让有用证据更靠前，提高上下文质量？ | 计划 |
| D：微调实验 | 较好的检索方案 + 微调后的 MiniCPM | 微调是否带来额外收益？ | 可选，取决于前期结果 |

实验 B、C 的具体实现根据基线错误分析决定，不保证每项改动都有效。

### 对照原则

- 尽量一次只改变一个主要因素。
- 对照检索方法时，尽量固定生成模型、提示词、输入预算和生成设置。
- 比较微调前后时，使用相同的检索结果和生成设置，减少其他因素的干扰。
- 保留有效和无效的实验结果，不能只记录提升的配置。
- 同时比较准确率、运行时间、模型调用次数和显存占用。
- 所有新增模型均需满足项目的单模型参数限制。

若需要进一步证明某个模块的贡献，再做针对性消融，例如从混合检索方案中移除语义检索，或从重排序方案中移除重排序。

## 6. 阶段四：按需进行微调

### 6.1 什么时候考虑微调

如果错误主要来自缺少证据，优先改进检索。

如果相关证据已经进入上下文，但模型仍频繁比较错误、误读时间关系或无法正确拒答，再考虑通过微调改善回答行为。

### 6.2 训练数据方案

候选方案是使用经过检查的“资料 + 问题 + 正确答案”样本训练 MiniCPM。出题模型可以与被训练模型不同，例如使用其他模型生成候选题，再检查后用于训练。

当前 MiniCPM 自动出题试验在 20 次尝试中没有获得通过筛选的样本，暴露了单篇题、事实混淆等问题。因此暂停扩充，先完成 RAG 基线和错误分析。

后续制作训练数据时应检查：

- 问题是否确实需要结合多篇文档。
- 答案是否受到资料支持。
- 引用的原文是否有效且相关。
- 是否混淆提议与实施、争议与定论、发布时间与事件时间。
- 是否存在重复、歧义或训练与评测重叠。

若使用官方问题作为训练资源，必须先明确划分训练、验证和测试用途，并披露重叠情况；不能把训练过的题目成绩描述成独立测试成绩。当前基线保持全部官方问题作为评测对象。

### 6.3 判断微调是否有效

将微调后的模型与相同检索条件下的原始 MiniCPM 比较。记录训练数据来源、样本数量、训练设置和资源消耗。微调是待验证的方案，不以“进行了训练”本身作为效果证据。

## 7. 评价方式

### 7.1 答题结果

- 全部 2,556 题的总体成绩。
- 推理、比较、时间、不可回答四类题目的分类成绩。
- 缺失和失败题目数量，不能从全量分母中删除。

当前本地评分器复现课程说明中的规则：预测与参考答案转成小写后，按空白分词，有词语交集即判为成功。该规则不同于常规完全匹配或标准 token F1。

**最终正式成绩必须使用老师分发的固定官方评分脚本复核。**本地复现结果和官方脚本运行结果要分别标明。

### 7.2 检索与资源分析

可补充统计参考文档覆盖率、完整参考文档集合的覆盖情况，并明确计算方式。这些指标仅用于事后分析。

同时记录模型名称与参数量、软件版本、硬件、模型调用次数、输入输出 token 数、运行时间及峰值显存。

公开测试集上的调试和参数选择需要如实披露，不将这些结果描述成隐藏测试性能。

## 8. 日志与最终交付

保留每题关联的检索结果、文档来源、实际模型输入、原始输出、最终答案、错误和重试记录。

当前基线主要输出：

- `predictions.json`：题号与最终简短答案；全量完成后覆盖 `q0000` 至 `q2555`。
- `execution_records.jsonl`：逐题检索、上下文、生成和运行记录。
- `summary.json`：进度、失败数量和资源统计。
- `scores_local.json`：本地复现评分规则的结果。
- `run_config.json`、`hardware.json`：配置、版本和硬件信息。

最终整理完整预测、官方评分输出、各组实验对照、成功与失败案例、可复现代码及项目报告。正式评分时生成的含参考答案的适配文件与最终预测文件分开保存。
